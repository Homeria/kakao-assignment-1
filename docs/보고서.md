### 1. 전체 틀 잡기 & 개발 진행 방향 정립
- AI 활용 내용
    - 틀 잡기
        - 해당 프로젝트는 Vanilla JS 버전의 Todo 프로젝트를 React로 마이그레이션 해보며 React 프레임워크를 직접 이용해보는 것임.
        - 더 나아가, JS와는 다른 코드 재사용성을 위한 컴포넌트 단위의 개발 등 React만의 개발 방법을 익히는데 의의를 둠.
        - 1차 과제처럼 Notion에 있는 2차 과제에 대하여 직접 정리하여 AI에게 제공하기 보다 Notion의 마크다운 글을 그대로 주는 것이 좋겠다고 판단함.
        - 그리고, 해당 과제가 마이그레이션이 목적인 만큼 Vanilla JS 버전의 Todo 프로젝트를 코드를 그대로 주는 것이 좋겠다고 판단함.
        - 이러한 과정으로 만들어진 문서가 `docs/작업_계획.md`임. 해당 문서는 개발을 해감에 따라 업데이트 되어 개발의 과정을 자세히 나타냄.
    
- 직접 진행한 것
    - 프로젝트의 조건 서술
        - 해당 프로젝트는 `kakao-assignment-1`이라는 하나의 Repository에서 진행하고, 1, 2, 3차 과제를 구분하기 위한 단위로 branch를 사용함.
        - 이에 따라, 3주차 5일차에 배운 `Github 협업`에 나오는 Git Workflow를 적용할 수 없었음.
        - 그렇기에, 기능에 대한 개발을 진행할 때 `feature/name` 등 별도의 브렌치로 진행하기 보다는 Commit 단위로 개발하는 것이 낫다고 판단했고, Commit 단위로 개발해달라는 조건을 직접 추가함.

- 직접 수정한 부분
    - 아키텍처 수정 (service-repository의 도입)
        - 1차 과제에서 구성한 아키텍처는 컴포넌트 단위 개발을 의도하고 만들었지만, 생각보다 가독성과 코드 재사용성이 좋지 않음을 느낌.
        - 2차 과제에서 AI에게 Vanilla JS 버전의 Todo 프로젝트 코드를 그대로 제공했더니, 이 가독성과 코드 재사용성이 좋지 않다고 판단되는 것을 그대로 반영함.

### 2. 전반적인 코딩과 테스트
- AI 활용 내용
    - 전반적인 코딩
        - `작업_계획.md`에서 정립한 개발 진행 방향에 따라 코딩을 진행하도록 함.
    - 테스트 케이스 구성
        - `1. 전체 틀 잡기` 단계에서 Codex에게 2차 과제 Notion 마크다운을 그대로 줬음에 따라, 테스트 케이스 구성과 이 테스트의 맥락을 Codex가 잘 파악하고 있다고 판단함.
        - 이에 따라, 테스트 케이스는 Codex에게 맡기고, 최종 테스트 전에 직접 전수조사 해보고, 적절하면 진행하는 것으로 함.
    - MCP를 통한 테스트
        - 1차 과제에서는 Gemini CLI, Antigravity CLI를 사용했었음.
        - 브라우저 MCP 연결이 가능했지만, 별도의 연결은 하지 않고 코드 분석과 테스트는 직접 수행했음.
        - 2차 과제에서는 Codex를 사용했음.
        - Codex는 별도의 MCP 연결을 하지 않아도 자동으로 수행하는 것을 보고 테스트를 직접 수행하도록 했고, 이에 따라 만들어진 문서가 `docs/검증_결과.md`임.
        - Codex의 자동 테스트를 거치면서 문제 없이 잘 동작하고 있다고 서술했으나, `npm run dev`를 통하여 직접 테스트를 진행해보면서, vite+react 프로젝트를 생성하면서 생긴 기본 css 스타일이, 작성했던 tailwind 스타일을 덮어쓰기 하며 렌더링 오류가 발생했음을 확인함.
        - Codex의 테스트가 완벽하지 않음을 알게 됐고, Codex의 테스트를 진행하기는 하지만 수동 테스트도 거치게 됐음. 즉, 2중 테스트를 거침.
- 직접 진행한 것
    - Commit
        - 전반적인 코딩은 Codex에 의존하였으나, 코드 점검과 보수는 직접 진행함.
        - 이에 따라, Commit 하기 전에 부족한 점이나 버그가 있으면 즉각적으로 프롬프트로 어느 부분에서 어느 부분이 어떤 문제가 있음을 자세히 서술하여 이를 반영하도록 유도함.
        - Commit 단계에서 조건을 모두 만족했다고 판단됐을 때는 커밋 메시지를 추천받고, 이를 어울리게 다시 포매팅하여 수동 Commit을 진행함.
    - 테스트
        - 앞서 말했듯이, Codex의 테스트는 완벽하지 않음. 특히 렌더링이나 디자인적 버그가 존재할 때 탐지하지 못하고, 코드의 원활한 작동을 테스트할 수 있었음.
        - 이에 따라, Codex의 테스트 후에 수동 테스트를 진행하여 Codex가 알 수 없던 영역의 테스트를 직접 수행함.
- 직접 수정한 부분
    - 컴포넌트 분할
        - 주간 뷰는 처음부터 카드 단위로 만들고 이를 리스트로 구성했음.
        - 그러나, TodoList 부분은 더 작은 단위의 컴포넌트로 쪼갤 수 있었으나 진행하지 않았음.
        - 오버엔지니어링 내지 분리할 필요가 없다고 판단했을 가능성이 높음.
        - 그러나 책임 분리 원칙을 준수하기 위해서, TodoInput과 TodoEdit을 각각의 컴포넌트로 분리하는 아이디어를 냈고, Codex가 이에 동의하여 분리 작업을 진행함. 이에 따라 단일 책임 원칙을 준수하고 코드 재사용성이 상승함.
