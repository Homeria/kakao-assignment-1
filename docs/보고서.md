# 3차 과제 보고서

## 과제 목표

이번 과제는 2차 과제에서 만든 React(Vite) 기반 Todo 앱을 Next.js App Router와 FastAPI 기반 풀스택 구조로 전환하는 작업이다.

중점적으로 확인한 목표는 다음과 같다.

- Next.js App Router의 파일 기반 라우팅 이해
- Server Component와 Client Component의 역할 구분
- FastAPI CRUD API와 SQLite 저장 흐름 구현
- localStorage 기반 상태 관리에서 서버 API 기반 데이터 흐름으로 전환
- Next.js API Route를 통한 프론트-백엔드 프록시 흐름 구현
- URL 쿼리 기반 필터와 검색 상태 관리
- 환경변수를 통한 프론트엔드와 백엔드 설정 분리

## 구현한 기능

### Todo CRUD

- Todo 생성
- Todo 목록 조회
- Todo 완료 상태 토글
- Todo 수정
- Todo 삭제
- 빈 입력값 방어
- 존재하지 않는 Todo 접근 시 not found 처리

### 날짜 기반 Todo

- 선택 날짜 기준 Todo 조회
- 이전 날짜 / 다음 날짜 이동
- 월요일부터 일요일까지 주간 날짜 카드 표시
- 이전 주 / 다음 주 이동
- 날짜별 Todo 개수 표시
- 오늘 날짜와 선택 날짜 구분

### 필터와 검색

- 전체 / 진행 중 / 완료 필터
- URL 쿼리 파라미터 기반 필터 상태 유지
- 검색어 URL 쿼리 파라미터 관리
- 검색 입력 디바운스
- 필터와 검색 동시 적용
- FastAPI 서버 기반 필터링과 검색

### 에러 처리

- 백엔드 서버 연결 실패 안내
- `BACKEND_URL` 누락 안내
- API Route에서 백엔드 연결 실패를 `503` JSON 응답으로 변환
- Todo 라우트의 `loading.tsx`, `error.tsx`, `not-found.tsx` 구성

## 2차 과제와 달라진 점

2차 과제에서는 Todo 데이터와 UI 상태를 브라우저 `localStorage`에 저장했다. 이번 과제에서는 Todo 데이터의 원본을 FastAPI 서버와 SQLite DB로 옮겼다.

2차 과제의 구조:

```text
React state
  -> localStorage Repository
  -> JSON 저장
```

3차 과제의 구조:

```text
Client Component
  -> Next.js API Route
  -> FastAPI
  -> SQLite
```

Server Component에서 데이터를 조회할 때는 브라우저를 거치지 않고 서버 함수가 FastAPI를 직접 호출한다.

```text
Server Component
  -> actions.ts
  -> FastAPI
  -> SQLite
```

이 변화로 새로고침 후에도 서버 DB를 기준으로 데이터를 복구할 수 있고, 필터와 검색을 클라이언트 배열 필터링이 아니라 서버 조회 조건으로 처리할 수 있게 됐다.

## Server Component와 Client Component 구분

### Server Component로 둔 영역

- `/todos` 목록 페이지의 초기 데이터 조회
- `/todos/[todoId]` 수정 페이지의 Todo 상세 조회
- 정적인 페이지 레이아웃
- 날짜, 필터, 검색 URL 파라미터 파싱

### Client Component로 둔 영역

- Todo 생성/수정 Form
- Todo 완료 토글
- Todo 삭제
- 검색 입력 디바운스

기준은 명확하게 잡았다. `useState`, `useEffect`, `useRouter`, `onClick`, `onChange` 같은 브라우저 인터랙션이 필요한 곳만 Client Component로 분리했다.

## API 흐름

브라우저에서 발생하는 요청은 FastAPI를 직접 호출하지 않고 Next.js API Route를 거친다.

```text
브라우저
  -> /api/todos
  -> app/api/todos/route.ts
  -> FastAPI /todos
  -> SQLite
```

이 구조를 통해 브라우저에는 실제 백엔드 주소를 노출하지 않고, CORS 문제도 줄일 수 있다.

## 환경변수 관리

프론트엔드와 백엔드의 환경변수를 분리했다.

```text
frontend/.env.local
BACKEND_URL=http://localhost:8000
NEXT_PUBLIC_API_URL=/api

backend/.env.local
DATABASE_URL=sqlite:///./todos.db
```

`BACKEND_URL`은 Next.js 서버에서만 사용하고, Client Component는 `/api` 경로를 통해 같은 Next.js 앱의 Route Handler를 호출한다.

## 구현하면서 고민한 점

### 백엔드 파일 분리 여부

현재 백엔드는 `main.py` 단일 파일에 DB 설정, 모델, 스키마, 엔드포인트가 함께 있다. 과제 조건에서는 단일 파일 구현도 자연스러운 흐름이라 우선 기능 완성에 집중했다.

다만 실제로 계속 사용할 앱이라면 다음 구조로 리팩토링할 수 있다.

```text
backend/
  main.py
  database.py
  models.py
  schemas.py
  routers/
    todos.py
```

### 에러 처리 범위

백엔드 서버가 꺼져 있을 때 처음에는 `fetch failed` 같은 원문 메시지만 보였다. 사용자가 다음 행동을 알 수 있도록 “FastAPI 서버가 실행 중인지 확인해주세요”라는 문구와 `503` JSON 응답 변환을 추가했다.

### 날짜 검증

프론트에서는 `YYYY-MM-DD` 형식 검증을 넣었다. 백엔드는 현재 `date`를 문자열로 받고 있어 Swagger UI에서 임의 문자열을 넣는 것까지는 막지 않는다. 이 부분은 이후 백엔드 검증 보강 커밋으로 개선할 수 있다.

## 회고

2차 과제에서는 React 상태와 localStorage를 연결하는 방식이 핵심이었다. 3차 과제에서는 같은 Todo 앱이지만 데이터의 원본이 브라우저에서 서버로 이동하면서 생각해야 할 지점이 많아졌다.

특히 Server Component와 Client Component를 구분하는 기준, API Route와 Server Action의 역할 차이, URL 상태를 서버 조회 조건으로 연결하는 흐름을 직접 구현하면서 Next.js App Router의 특징을 더 명확히 이해할 수 있었다.

아쉬운 점은 백엔드 날짜 검증과 계층 분리를 아직 완전히 마무리하지 않았다는 점이다. 기능 요구사항을 먼저 닫은 뒤, 리팩토링 커밋에서 프론트 API 계층과 백엔드 파일 구조를 더 정리해볼 예정이다.
