# 프론트엔드 리팩토링 결과

## 목적

프론트엔드 리팩토링은 기능 동작을 바꾸는 것이 아니라, Todo 앱의 API 호출, 이벤트 처리, URL 상태 관리, 데이터 준비, UI 표현 책임을 더 명확히 나누기 위해 진행했다.

리팩토링 전에는 `app/lib`에 여러 성격의 유틸이 섞여 있었고, 일부 컴포넌트가 API 요청 옵션이나 에러 처리 방식을 직접 알고 있었다. 리팩토링 후에는 역할별 모듈과 작은 UI 컴포넌트를 통해 코드 위치와 책임을 더 쉽게 추적할 수 있게 정리했다.

## 진행 결과

### 1. HTTP 에러 처리 기반 분리

- `lib/api/http.ts`에 공통 HTTP 유틸을 분리했다.
- API 실패 응답을 `ApiRequestError`로 표현하도록 정리했다.
- JSON 응답 본문 파싱과 에러 메시지 추출 로직을 서버/클라이언트 caller가 공유하게 했다.

#### 기대효과

- 백엔드 404, 422, 500, 503 응답 메시지 처리 방식이 더 일관된다.
- 빈 응답이나 잘못된 JSON 본문이 들어와도 파싱 예외가 화면에 직접 노출될 가능성이 줄었다.

### 2. Todo API client 추가

- `lib/todo/client.ts`에 Todo 전용 API caller를 추가했다.
- `createTodo`, `updateTodo`, `deleteTodo`, `toggleTodo`로 API 요청 의도를 함수 이름에 드러냈다.
- 컴포넌트가 HTTP method, header, body 직렬화 방식을 직접 조립하지 않도록 했다.

#### 기대효과

- Todo 관련 API 요청이 한곳에 모였다.
- 이후 Todo API 경로나 요청 방식이 바뀌어도 컴포넌트 수정 범위가 줄어든다.

### 3. Todo 이벤트 핸들러 정리

- `TodoForm`과 `TodoItem`에서 직접 `requestClientApi`를 호출하던 코드를 제거했다.
- 에러 fallback 메시지 처리를 `getErrorMessage` 유틸로 분리했다.
- 저장, 완료 토글, 삭제 이벤트 핸들러가 화면 상태 처리에 더 집중하도록 정리했다.

#### 기대효과

- 이벤트 핸들러의 중복 코드가 줄었다.
- API 요청 세부 사항과 UI 이벤트 흐름의 결합도가 낮아졌다.

### 4. Todo form 검증 로직 분리

- `lib/todo/validation.ts`에 폼 입력 검증과 Todo payload 변환 로직을 분리했다.
- 제목 trim, 빈 제목 검증, 날짜 형식 검증을 폼 컴포넌트 밖으로 이동했다.

#### 기대효과

- `TodoForm`은 입력 상태와 제출 흐름에 집중한다.
- 검증 정책을 변경할 때 수정 위치가 명확해졌다.

### 5. URL 상태 helper 정리

- `lib/url/searchParams.ts`에 의미 단위 URL helper를 추가했다.
- 날짜 이동, 주간 이동, 필터, 검색, Todo 생성/수정 링크 생성을 각각 전용 함수로 분리했다.
- `/todos`에서 `/todos/new` 링크를 만들 때 문자열 `replace`를 사용하던 흐름을 제거했다.

#### 기대효과

- URL query 정책이 한 파일에 모였다.
- 컴포넌트에서 어떤 URL 상태를 바꾸는지 함수 이름으로 드러난다.

### 6. API Route 프록시 helper 적용

- `lib/api/proxy.ts`에 Next.js API Route용 프록시 helper를 추가했다.
- Route Handler의 반복적인 `try/catch`, FastAPI fetch, proxy response 변환 로직을 줄였다.
- POST/PUT 요청 body 전달 로직을 공통 함수로 분리했다.

#### 기대효과

- API Route 파일이 경로와 method 중심으로 단순해졌다.
- 이후 API Route가 추가될 때 같은 프록시 패턴을 재사용할 수 있다.

### 7. lib 디렉터리 역할 분리

- `app/lib` 하위 파일을 역할별 디렉터리로 분리했다.

```text
frontend/app/lib
├─ api/
│  ├─ backend.ts
│  ├─ client.ts
│  ├─ errors.ts
│  ├─ http.ts
│  └─ proxy.ts
├─ date/
│  └─ index.ts
├─ todo/
│  ├─ client.ts
│  ├─ pageData.ts
│  ├─ types.ts
│  └─ validation.ts
└─ url/
   └─ searchParams.ts
```

#### 기대효과

- API, Todo, URL, 날짜 유틸의 위치 기준이 분명해졌다.
- 다음 리팩토링이나 기능 추가 시 파일 탐색 비용이 줄어든다.

### 8. Todo 페이지 데이터 준비 로직 분리

- `/todos/page.tsx`의 Todo 조회, 주간 개수 계산, fallback 데이터 생성을 `lib/todo/pageData.ts`로 이동했다.
- 페이지 컴포넌트는 URL 상태 준비와 JSX 조립에 집중하도록 정리했다.

#### 기대효과

- 서버 데이터 준비 로직과 화면 렌더링 책임이 분리되었다.
- 이후 정렬, 통계, 날짜 범위 조회 같은 기능을 추가하기 쉬워졌다.

### 9. 반복 UI 요소 공통화

- `components/ui` 하위에 작은 공통 UI 컴포넌트를 추가했다.
  - `Button`
  - `ButtonLink`
  - `ErrorMessage`
  - `PageCard`
- Todo 목록, 생성, 수정, 에러, not found, loading 화면의 반복 className을 줄였다.

#### 기대효과

- 버튼, 에러 박스, 카드 스타일이 더 일관되게 유지된다.
- 화면 파일에서 핵심 구조가 더 잘 보인다.

### 10. 디버그 채널 추가

- `/todos` 헤더에 아이콘 버튼으로 여는 디버그 채널을 추가했다.
- 현재 URL query, 선택 날짜, 주 시작일, 필터, 검색어를 표시한다.
- Todo API path/query와 선택 날짜 Todo 수, 주간 Todo 통계를 표시한다.
- `/api/debug/health`를 통해 백엔드 health 상태를 확인한다.

#### 기대효과

- 새로고침이나 날짜 이동 후 현재 화면 상태를 빠르게 확인할 수 있다.
- Next.js API Route와 FastAPI 연결 상태를 프론트엔드에서 검증할 수 있다.

## 최종 구조 요약

- `components/todo`: Todo 목록, 항목, 폼, 검색 UI
- `components/date`: 날짜 헤더와 주간 날짜 선택 UI
- `components/filter`: Todo 상태 필터 UI
- `components/debug`: Todo 화면 디버그 채널 UI
- `components/ui`: 반복 UI 표현을 담당하는 작은 공통 컴포넌트
- `lib/api`: 서버/클라이언트 API caller, HTTP error, proxy helper
- `lib/todo`: Todo 타입, Todo client, validation, 페이지 데이터 준비
- `lib/url`: URL search params 파싱과 href 생성
- `lib/date`: 날짜 계산과 표시 유틸
- `lib/debug`: 디버그 채널 상태 변환과 health 확인 유틸
