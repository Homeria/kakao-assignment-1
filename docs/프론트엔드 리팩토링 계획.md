# 프론트엔드 리팩토링 계획

## 목적

현재 프론트엔드는 과제 조건을 만족하는 기능 구현은 완료된 상태다. 다만 Todo 기능이 늘어나거나 에러/로딩/검증 정책이 바뀔 경우, API 호출부와 화면 이벤트 처리부에 비슷한 코드가 반복될 가능성이 있다.

이번 리팩토링의 목적은 기능을 바꾸는 것이 아니라, 기존 동작을 유지하면서 다음 항목을 개선하는 것이다.

- API 호출 방식과 에러 메시지 처리 방식 통일
- Todo 생성/수정/삭제/완료 토글 이벤트 처리의 중복 축소
- URL 쿼리 상태 조작 로직의 사용 방식 정리
- 반복되는 UI 표현을 작게 공통화
- 페이지 컴포넌트의 데이터 준비 책임과 화면 조립 책임 분리

## 현재 구조 요약

- `app/actions.ts`: Server Component에서 사용하는 Todo 조회 함수와 Server Action 후보 함수
- `app/lib/api.ts`: 서버 환경에서 FastAPI를 호출하는 공통 fetch 유틸
- `app/lib/clientApi.ts`: Client Component에서 Next.js API Route를 호출하는 fetch 유틸
- `app/api/todos/*`: Next.js API Route 프록시
- `app/lib/searchParams.ts`: 날짜, 주간 시작일, 필터, 검색어 URL 상태 관리
- `app/components/todo/*`: Todo 목록, 아이템, 폼, 검색 UI
- `app/components/date/*`: 날짜 헤더와 주간 날짜 선택 UI
- `app/todos/page.tsx`: Todo 목록 페이지 데이터 조회와 화면 조립

## 리팩토링 후보

### 1. API caller 계층 정리

#### 문제점

- `app/lib/api.ts`와 `app/lib/clientApi.ts`가 각각 응답 본문 파싱, 에러 메시지 추출, 204 응답 처리 로직을 따로 가지고 있다.
- 서버 API 호출은 `BackendRequestError`를 사용하지만, 클라이언트 API 호출은 일반 `Error`만 던진다.
- Client Component에서는 매번 `requestClientApi<Todo>(...)`에 URL, method, headers, body를 직접 넘기고 있다.
- `Content-Type: application/json` 선언이 `actions.ts`, `TodoForm.tsx`, `TodoItem.tsx`, API Route에 반복된다.

#### 개선 방향

- `app/lib/http.ts` 같은 공통 HTTP 유틸을 추가한다.
  - `JSON_HEADERS`
  - `readResponseBody`
  - `getErrorMessageFromResponse`
  - `ApiRequestError`
- 서버용 FastAPI caller와 브라우저용 Next API caller가 같은 에러 메시지 파싱 함수를 사용하게 만든다.
- Client Component용 Todo API 래퍼를 추가한다.
  - `createTodo(input)`
  - `updateTodo(todoId, input)`
  - `deleteTodo(todoId)`
  - `toggleTodo(todo)`
- 컴포넌트에서는 HTTP 세부 옵션 대신 Todo API 함수만 호출하게 한다.

#### 기대효과

- 에러 메시지 정책이 바뀌어도 한 곳에서 수정할 수 있다.
- 컴포넌트가 `fetch` 옵션과 응답 형식을 알 필요가 줄어든다.
- 백엔드 통신 실패, 404, 422, 503 처리 방식이 서버/클라이언트에서 더 일관된다.
- 이후 Todo 외 API가 추가되어도 같은 호출 패턴을 재사용할 수 있다.

### 2. Client event handler 중복 축소

#### 문제점

- `TodoForm.tsx`와 `TodoItem.tsx`에 다음 패턴이 반복된다.
  - 제출/수정/삭제 전 에러 초기화
  - pending 상태 설정
  - API 호출
  - 실패 시 `error instanceof Error ? error.message : fallback` 처리
  - 성공 시 `router.refresh()` 또는 `router.push()`
- 삭제, 토글, 저장 로직이 모두 컴포넌트 내부에 있어 UI JSX와 비동기 흐름이 함께 커지고 있다.

#### 개선 방향

- `app/lib/errors.ts`에 `getErrorMessage(error, fallbackMessage)` 유틸을 둔다.
- 단순한 pending/error 상태 관리를 위한 작은 훅을 검토한다.
  - 예: `useAsyncAction`
  - 단, 현재 규모에서는 훅이 과하면 `getErrorMessage`와 Todo API 래퍼만 먼저 적용한다.
- `TodoItem`의 토글/삭제 API 호출은 Todo API 래퍼로 이동한다.
- `TodoForm`의 create/edit 분기에서 직접 HTTP 요청을 만들지 않고 Todo API 래퍼를 호출한다.

#### 기대효과

- 컴포넌트가 화면 상태와 이벤트 연결에 더 집중할 수 있다.
- 에러 메시지 fallback 로직이 반복되지 않는다.
- 이벤트 핸들러가 짧아져 이후 테스트와 수정이 쉬워진다.

### 3. Todo form 검증 로직 분리

#### 문제점

- `TodoForm.tsx` 내부에서 제목 trim, 빈 제목 검증, 날짜 형식 검증, 요청 body 생성까지 모두 처리한다.
- 프론트엔드 검증 규칙이 늘어나면 폼 컴포넌트가 계속 커질 가능성이 있다.
- 현재 백엔드 날짜 검증은 아직 강화 전이므로, 프론트엔드와 백엔드 검증 책임을 명확히 구분할 필요가 있다.

#### 개선 방향

- `app/lib/todoValidation.ts`를 추가한다.
  - `validateTodoFormInput`
  - `toTodoCreateInput`
  - `toTodoUpdateInput`
- 제목 trim과 날짜 형식 검증을 폼 외부 함수로 분리한다.
- 날짜가 선택 사항인지 필수인지 정책을 문서화하고, 현재 UI에서는 날짜 필수 입력으로 유지한다.

#### 기대효과

- 폼 UI와 입력 검증 정책이 분리된다.
- 생성/수정에서 같은 검증 규칙을 안정적으로 공유할 수 있다.
- 추후 백엔드 날짜 검증 강화 시 프론트엔드 검증과 맞춰보기 쉽다.

### 4. URL search params 조작 사용성 개선

#### 문제점

- `createTodoSearchHref(currentSearchParams, updates)`는 잘 동작하지만 호출부가 많다.
- 날짜 이동, 주간 이동, 필터 변경, 검색어 변경이 모두 같은 저수준 함수를 직접 호출한다.
- `TodoSearch.tsx`에서는 `URLSearchParams`를 `useMemo`로 만들고 debounce 후 직접 href를 생성한다.

#### 개선 방향

- `searchParams.ts`에 의미가 드러나는 helper를 추가한다.
  - `createDateHref`
  - `createWeekHref`
  - `createFilterHref`
  - `createSearchHref`
  - `createNewTodoHref`
  - `createEditTodoHref`
- Client Component에서 URL 변경을 자주 다루게 되면 `useTodoSearchNavigation` 같은 훅을 검토한다.
- 먼저 helper 함수만 추가해 기존 구조를 크게 흔들지 않는다.

#### 기대효과

- 날짜/필터/검색 UI 컴포넌트의 의도가 더 잘 드러난다.
- 쿼리 파라미터 정책이 바뀌어도 `searchParams.ts` 중심으로 수정할 수 있다.
- URL 상태 관리 실수가 줄어든다.

### 5. Route Handler 프록시 중복 축소

#### 문제점

- `app/api/todos/route.ts`와 `app/api/todos/[todoId]/route.ts`는 다음 패턴을 반복한다.
  - `try`
  - `fetchBackendResponse`
  - `toProxyResponse`
  - `catch`
  - `toProxyErrorResponse`
- 요청 body를 그대로 전달하는 POST/PUT에서 headers/body 전달 방식도 반복된다.

#### 개선 방향

- `app/lib/proxy.ts`를 추가한다.
  - `proxyBackendRequest(path, init?)`
  - `createJsonProxyInit(request, method)`
- Route Handler는 경로와 method만 명확히 드러내도록 줄인다.
- 단, Next.js Route Handler의 가독성이 떨어질 정도로 추상화하지 않는다.

#### 기대효과

- 프록시 에러 처리 누락 가능성이 줄어든다.
- 이후 API Route가 추가되어도 같은 패턴으로 확장할 수 있다.
- 라우트 파일은 라우팅 정보에 더 집중한다.

### 6. 반복 UI 요소 공통화

#### 문제점

- 주요 버튼 스타일이 여러 파일에 반복된다.
  - `TodoForm.tsx`
  - `todos/page.tsx`
  - `todos/error.tsx`
  - `todos/not-found.tsx`
- 에러 박스 스타일도 여러 곳에서 직접 className으로 작성된다.
- 카드형 section 스타일도 페이지마다 반복된다.

#### 개선 방향

- 과한 디자인 시스템 대신 작은 공통 컴포넌트만 추가한다.
  - `ButtonLink`
  - `Button`
  - `ErrorMessage`
  - `PageCard`
- 기존 Tailwind 스타일을 유지하되 className 반복을 줄인다.
- 모든 UI를 한 번에 바꾸기보다 Todo 화면에서 반복되는 부분부터 적용한다.

#### 기대효과

- 버튼, 에러 박스, 카드 스타일이 더 일관된다.
- 디자인 수정이 필요할 때 여러 파일을 동시에 수정하지 않아도 된다.
- JSX에서 핵심 구조가 더 잘 보인다.

### 7. Todo page 데이터 준비 로직 분리

#### 문제점

- `app/todos/page.tsx` 안에 다음 책임이 함께 있다.
  - URL search params 파싱
  - Todo 목록 조회
  - 주간 Todo 개수 계산
  - 에러 fallback 데이터 구성
  - 화면 렌더링
- 현재는 감당 가능한 크기지만, 이후 통계나 정렬 기능이 추가되면 페이지 파일이 빠르게 비대해질 수 있다.

#### 개선 방향

- `app/lib/todoPageData.ts` 또는 `app/todos/data.ts`로 데이터 준비 로직을 분리한다.
  - `getTodoCountByDate`
  - `getTodoPageData`
  - `getTodoPageFallbackData`
- 페이지 컴포넌트는 search params를 준비하고 UI를 조립하는 역할에 집중한다.

#### 기대효과

- 서버 데이터 준비 로직을 독립적으로 읽고 테스트하기 쉬워진다.
- 페이지 컴포넌트의 JSX 흐름이 단순해진다.
- 이후 정렬, 통계, 날짜 범위 조회 등의 기능 추가가 쉬워진다.

## 우선순위

### 1순위

- API caller 계층 정리
- Client event handler 중복 축소
- Todo form 검증 로직 분리

이 세 항목은 실제 기능 코드의 중복과 책임 섞임을 줄이는 효과가 가장 크다.

### 2순위

- URL search params helper 추가
- Route Handler 프록시 중복 축소
- Todo page 데이터 준비 로직 분리

기능 확장에 대비하는 성격이 강하다. 1순위 작업 후에도 파일이 복잡하게 느껴지면 진행한다.

### 3순위

- 반복 UI 요소 공통화

가독성과 스타일 일관성에는 도움이 되지만, 현재 기능 안정성에 직접적인 영향은 작다. 작은 컴포넌트 위주로 제한해서 진행한다.

## 권장 진행 순서

1. 공통 에러 유틸과 Todo API client 래퍼 추가
2. `TodoForm.tsx`, `TodoItem.tsx`가 Todo API client를 사용하도록 변경
3. Todo form 입력 검증 로직 분리
4. URL helper를 추가하고 날짜/필터/검색 컴포넌트 호출부 정리
5. Route Handler 프록시 helper 적용
6. `/todos` 페이지 데이터 준비 로직 분리
7. 반복 UI 컴포넌트는 변경 범위가 큰 파일을 건드릴 때 함께 소규모 적용

## 커밋 단계

### 리팩토링 커밋 1. HTTP 에러 처리 기반 정리

#### 목표

서버 API caller와 클라이언트 API caller가 공통으로 사용할 수 있는 HTTP 에러 처리 기반을 만든다.

#### 작업 범위

- `app/lib/http.ts` 또는 유사한 공통 유틸 추가
- JSON headers 상수 분리
- 응답 본문 파싱 함수 분리
- FastAPI validation error와 일반 API error 메시지 추출 함수 분리
- 서버/클라이언트에서 함께 쓸 수 있는 `ApiRequestError` 형태 검토

#### 제외 범위

- 컴포넌트 이벤트 핸들러 변경
- Todo API client 래퍼 적용
- UI 변경

#### 검증

- `npm.cmd run lint`
- `npm.cmd run build`
- 백엔드 중단 시 기존 에러 메시지가 유지되는지 확인

### 리팩토링 커밋 2. Todo API client 래퍼 추가

#### 목표

Client Component가 HTTP 세부 옵션을 직접 작성하지 않도록 Todo 전용 API 호출 함수를 만든다.

#### 작업 범위

- `app/lib/todoClient.ts` 또는 유사한 파일 추가
- `createTodo`
- `updateTodo`
- `deleteTodo`
- `toggleTodo`
- 기존 `requestClientApi`는 내부 구현으로 유지하거나 Todo client에서만 사용하도록 정리

#### 제외 범위

- `TodoForm.tsx`, `TodoItem.tsx` 적용은 다음 커밋에서 진행
- URL search params helper 변경
- Route Handler 변경

#### 검증

- `npm.cmd run lint`
- `npm.cmd run build`

### 리팩토링 커밋 3. Todo 이벤트 핸들러 정리

#### 목표

`TodoForm.tsx`와 `TodoItem.tsx`가 Todo API client를 사용하도록 변경하고, 이벤트 핸들러의 중복을 줄인다.

#### 작업 범위

- `TodoForm.tsx`의 생성/수정 요청을 Todo API client 호출로 변경
- `TodoItem.tsx`의 완료 토글/삭제 요청을 Todo API client 호출로 변경
- 에러 메시지 fallback 유틸 적용
- 직접 작성하던 `Content-Type`, `JSON.stringify`, API path 중복 제거

#### 제외 범위

- 폼 검증 정책 변경
- 디자인 변경
- URL query 정책 변경

#### 검증

- `npm.cmd run lint`
- `npm.cmd run build`
- Todo 생성, 수정, 삭제, 완료 토글 수동 확인

### 리팩토링 커밋 4. Todo form 검증 로직 분리

#### 목표

폼 UI와 입력 검증 정책을 분리해 생성/수정 폼의 책임을 가볍게 만든다.

#### 작업 범위

- `app/lib/todoValidation.ts` 추가
- 제목 trim 검증 분리
- 날짜 `YYYY-MM-DD` 검증 분리
- Todo 생성/수정 input 변환 함수 분리
- `TodoForm.tsx`에서 검증 결과만 사용하도록 변경

#### 제외 범위

- 백엔드 날짜 검증 강화
- 날짜 입력 UI 변경
- Todo API Route 변경

#### 검증

- `npm.cmd run lint`
- `npm.cmd run build`
- 빈 제목, 잘못된 날짜, 정상 저장 케이스 수동 확인

### 리팩토링 커밋 5. URL 상태 helper 정리

#### 목표

날짜, 주간 이동, 필터, 검색, 생성/수정 링크 생성 로직의 의도를 더 명확히 드러낸다.

#### 작업 범위

- `searchParams.ts`에 의미 단위 helper 추가
  - 날짜 이동 href
  - 주간 이동 href
  - 필터 href
  - 검색 href
  - Todo 생성 href
  - Todo 수정 href
- `DateHeader.tsx`, `WeeklyView.tsx`, `WeeklyDayCard.tsx`, `FilterTabs.tsx`, `TodoSearch.tsx`, `TodoList.tsx` 호출부 정리

#### 제외 범위

- URL query 파라미터 이름 변경
- 검색 debounce 정책 변경
- 화면 디자인 변경

#### 검증

- `npm.cmd run lint`
- `npm.cmd run build`
