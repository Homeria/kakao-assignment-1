# 백엔드 리팩토링 계획

## 목적

초기 백엔드는 기능 구현이 완료되어 있었지만 `backend/main.py` 하나에 앱 생성, DB 설정, SQLAlchemy 모델, Pydantic 스키마, CRUD 엔드포인트가 모두 들어 있었다.

이번 리팩토링의 목적은 기능을 추가하거나 응답 구조를 바꾸는 것이 아니라, 같은 동작을 유지한 채 파일 역할을 분리해 유지보수성을 높이는 것이다.

## 리팩토링 원칙

- 기능 추가를 하지 않는다.
- API 경로를 변경하지 않는다.
- 응답 JSON 구조를 변경하지 않는다.
- DB 테이블 구조를 변경하지 않는다.
- Swagger UI 동작을 의도적으로 바꾸지 않는다.
- 날짜 형식 검증 추가는 이번 리팩토링 범위에서 제외한다.

## 진행 결정

백엔드는 프론트엔드 중심 과제의 보조 서버 역할이므로, 과한 계층 분리보다 읽기 쉬운 최소 분리를 우선했다.

최종적으로는 DB 연결, SQLAlchemy 모델, Pydantic 스키마만 `backend/app` 패키지로 분리하고, 라우터 분리는 보류했다.

이 결정으로 `main.py`에는 FastAPI app 설정과 실제 endpoint 흐름이 남아 있고, 데이터 계층과 스키마 정의는 별도 파일에서 확인할 수 있게 됐다.

## 초기 문제점

### 1. `main.py`의 책임이 많다

초기 `main.py`는 다음 책임을 모두 가졌다.

- `.env.local` 로드
- DB URL 설정
- SQLAlchemy engine/session/Base 설정
- Todo SQLAlchemy 모델 정의
- Todo Pydantic 스키마 정의
- FastAPI app 생성
- CORS 설정
- root/health endpoint 정의
- Todo CRUD endpoint 정의
- Todo 조회 필터/검색 쿼리 작성
- Todo 존재 여부 확인 helper 정의

파일이 작을 때는 큰 문제가 아니지만, 기능이 조금만 늘어나도 수정 위치를 찾기 어려워진다.

### 2. 도메인 계층과 HTTP 계층이 섞여 있다

Todo 모델, 요청/응답 스키마, 라우터 함수가 같은 파일에 있어 각 코드의 목적이 눈에 바로 들어오지 않는다.

### 3. 이후 검증과 확장이 어려워진다

날짜 검증, 정렬, 통계, 사용자별 Todo 같은 기능이 추가될 경우 현재 구조에서는 `main.py`가 계속 커질 가능성이 높다.

## 최종 반영 구조

```text
backend/
├─ app/
│  ├─ __init__.py
│  ├─ database.py
│  ├─ models.py
│  └─ schemas.py
├─ main.py
├─ requirements.txt
└─ README.md
```

### 파일별 역할

- `backend/main.py`: FastAPI app 생성, CORS 설정, DB 테이블 생성, root/health/Todo endpoint 정의.
- `backend/app/database.py`: 환경변수 로드, DB engine, `SessionLocal`, `Base`, `get_db`.
- `backend/app/models.py`: SQLAlchemy 모델 정의.
- `backend/app/schemas.py`: Pydantic 요청/응답 스키마 정의.

### 보류한 구조

아래 구조는 검토했지만 이번 단계에서는 적용하지 않았다.

```text
backend/app/main.py
backend/app/routers/health.py
backend/app/routers/todos.py
```

라우터까지 분리하면 파일 수와 import 경로가 늘어나는 대신 얻는 이점은 아직 크지 않다고 판단했다. 현재 규모에서는 `main.py`에 endpoint 흐름이 모여 있는 편이 Swagger UI와 실제 API 동작을 따라가기 쉽다.

## 커밋 단계

### 백엔드 리팩토링 커밋 1. 앱 패키지와 DB/model/schema 분리

#### 목표

`main.py`에 섞여 있는 DB 설정, SQLAlchemy 모델, Pydantic 스키마를 `app` 패키지로 분리한다.

#### 작업 범위

- `backend/app/__init__.py` 추가
- `backend/app/database.py` 추가
- `backend/app/models.py` 추가
- `backend/app/schemas.py` 추가
- 기존 `main.py`의 DB/model/schema import 경로 정리
- 기능 동작은 기존과 동일하게 유지

#### 제외 범위

- router 분리
- API 경로 변경
- 날짜 검증 추가
- DB 스키마 변경

#### 검증

- `.\venv\Scripts\python.exe -m py_compile main.py app\*.py`
- `/health`와 `/todos` 기본 응답 스모크 확인

### 백엔드 리팩토링 커밋 2. health/todos 라우터 분리

#### 목표

root/health endpoint와 Todo CRUD endpoint를 FastAPI router로 분리한다.

#### 작업 범위

- `backend/app/routers/__init__.py` 추가
- `backend/app/routers/health.py` 추가
- `backend/app/routers/todos.py` 추가
- `backend/app/main.py`에서 router 등록
- `backend/main.py`는 `app.main`의 app을 export하는 진입점으로 축소

#### 제외 범위

- API 응답 구조 변경
- Todo CRUD 로직 변경
- 쿼리 파라미터 이름 변경
- CORS 정책 변경

#### 검증

- `.\venv\Scripts\python.exe -m py_compile main.py app\*.py app\routers\*.py`
- `GET /`
- `GET /health`
- `POST /todos`
- `GET /todos`
- `PUT /todos/{todo_id}`
- `DELETE /todos/{todo_id}`

#### 최종 결정

이 단계는 보류했다.

기능 요구사항과 현재 코드 규모를 고려하면 라우터 분리보다 `database`, `models`, `schemas` 분리만으로도 가독성 개선 효과가 충분하다고 판단했다.

### 백엔드 리팩토링 커밋 3. 백엔드 구조 문서화와 최종 검증

#### 목표

분리된 백엔드 구조와 검증 결과를 문서에 반영한다.

#### 작업 범위

- `backend/README.md` 구조 설명 갱신
- `docs/검증 결과.md` 백엔드 리팩토링 검증 항목 추가
- 필요하면 `docs/보고서.md`에 백엔드 구조 분리 내용 간단히 추가

#### 제외 범위

- 코드 추가 리팩토링
- 기능 변경

#### 검증

- 문서에 실제 파일 구조가 맞게 반영되어 있는지 확인
- 최종 py_compile와 API 스모크 결과를 기록

#### 최종 결정

이 문서와 최종 검증 문서에 1단계 리팩토링 결과만 반영한다. 라우터 분리 결과 문서는 작성하지 않는다.

## 예상 효과

- `main.py`가 FastAPI app 설정과 endpoint 흐름에 집중한다.
- DB 연결, 모델, 스키마 책임이 분리된다.
- Swagger UI와 API 경로는 그대로 유지하면서 코드 탐색성이 좋아진다.
- 추후 날짜 검증 강화나 테스트 추가를 더 작은 파일 단위로 진행할 수 있다.

## 리스크와 대응

### import 경로 오류

파일 이동 후 상대 import가 깨질 수 있다. 각 커밋마다 `py_compile`로 전체 Python 파일을 확인한다.

### DB 테이블 생성 시점 변경

기존에는 `main.py` import 시점에 `Base.metadata.create_all(bind=engine)`이 실행됐다. 리팩토링 후에도 FastAPI app 생성 시 동일하게 실행되도록 유지한다.

### API 동작 변경 가능성

라우터 분리 과정에서 path prefix나 response model이 달라질 수 있다. 기존 경로와 응답 모델을 그대로 옮기고 API 스모크로 확인한다.

최종적으로 라우터 분리는 보류했기 때문에 path prefix 변경 리스크는 발생하지 않았다.
